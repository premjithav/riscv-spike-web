Running Spike in a Browser Tab

11 October 2026HDG-Team1

Spike, the reference RISC-V ISA simulator, now runs inside a browser tab, with its interactive debugger, and its output matches native Spike instruction for instruction. Over three days we built that port as an open-source project, riscv-spike-web.

Why a browser? A failing test is easier to discuss when anyone can open a link, step to the failing PC and inspect registers, with nothing to install. The same build is useful in workshops, where students can watch an ISA test execute instruction by instruction.

This post covers how the port works without changing Spike's source, how we proved it correct, how it stays easy to update, and how an AI assistant (Claude, in Cowork mode) did much of the hands-on work.

Porting Spike without touching its source

Spike builds for WebAssembly with Emscripten and its own unmodified autoconf build; every adjustment is a compiler flag, a linker setting or code in the web page. That rule mattered because Spike changes often, and a fork with local patches would fall behind.

An earlier version carried a one-line patch to mmu.cc. Replacing it with a flag produced a .wasm file of exactly the same size, 7,873,441 bytes.

Proving it matches native Spike

Every build has to pass a verification gate before it counts: the riscv-tests suite on native and wasm Spike, plus a byte-for-byte comparison of their instruction traces.

Throughput, 140M-instruction RV64 loop~240 MIPS (0.59 s)~120 MIPS (1.18 s, incl. ~0.2 s startup)

One test, rv64ui-p-ma_data, is skipped on both: Spike doesn't emulate misaligned accesses by default, and it fails identically on native and wasm. The rv64ua atomics tests are built with -march=rv64g, because the pinned GCC 14 lacks the Zacas extension that upstream riscv-tests now asks for.

WebAssembly runs at about half native speed. That's fine for debugging, sharing and teaching. High-volume CI regression stays on native Spike.

A debugger in a browser tab

The demo page runs Spike in a Web Worker and has two modes: Run, which executes a program to completion, and Debug, which drives Spike's own interactive debugger (spike -d). It ships with ten benchmarks, seven ISA tests and a hello program, and accepts any bare-metal RV64 ELF.

The hard part was the debugger. Spike waits for each command with a blocking read(), and a web page cannot pause WebAssembly until the user types without special cross-origin headers that hosts such as GitHub Pages don't send. Spike is deterministic, though, so the page replays instead: each new command re-runs the program from reset with the whole command history as input. The same program and commands always reach the same state, so the transcript looks like a live session, and Undo works for free by dropping the last command.

Three small pieces made it work:

  • Spike reads debugger input from file descriptor 2, which works on a real terminal. The worker redirects reads on fd 2 to stdin, with no change to Spike.
  • The page reads the ELF symbol table, so until pc 0 main works even though Spike only accepts hex addresses.
  • The status bar shows the current PC as symbol+offset, for example main+0xa.

The cost is that every command replays everything before it. Demo programs replay in milliseconds; a program that runs billions of instructions before the point of interest would be slow.

Built to follow upstream, and open source

Moving to a new Spike release is one command, and the update is kept only if the verification gate passes. Spike, riscv-tests and the Emscripten SDK are git submodules that are never edited, and build trees are separate per Spike commit, so a new version always builds from scratch.

./scripts/update-spike.sh            # latest upstream master
./scripts/update-spike.sh <sha|tag>  # a specific version

The script fetches the new commit, rebuilds native and wasm Spike, the tests and the demo, then runs the gate. If everything passes it commits the new submodule pointer; if anything fails it switches back to the previous commit and keeps the failed build for inspection.

The project is published under BSD-3-Clause, the same license as Spike and riscv-tests. A GitHub Actions workflow builds and verifies every push, publishes the demo to GitHub Pages from main, and runs a weekly build against the latest upstream Spike as an early warning. The demo is plain static files, so it can also be hosted on any web server; ours also runs at premjith.in/riscv-spike-web.

How AI tools were used

Most of the hands-on work was done by Claude, Anthropic's AI assistant, running in Cowork mode in the Claude desktop app; the engineer set direction, made the decisions, and did the steps that needed his own accounts or administrator rights. Claude didn't just suggest commands: it ran them, read the output, and fixed what broke.

It worked in two places:

  • A cloud workspace (Ubuntu 24.04) for anything needing tools or network access the laptop sandbox lacked: building static dtc binaries and browser testing.
  • A sandboxed Linux VM on the engineer's laptop, with the project folder mounted. Builds, test runs and git commits happened here, directly in the real repository. This shell only became available partway through, after the laptop user was added to the kvm group; before that, Claude could only copy files in and out.

Where the human stayed in the loop

The engineer made every decision that changed scope or touched an account: the license and copyright line, the repository name, and whether to publish. Some steps were his by design:

  • Credentials. Pushing to GitHub needs a GitHub login, which stayed on the laptop. Claude handed over git push instead of asking for a token.
  • Administrator steps. Joining the kvm group with sudo usermod, and installing Emscripten's toolchain from a network the sandbox couldn't reach.
  • Protected files. The sandbox refuses to write CI workflows and Makefiles; Claude sent those two files for the engineer to place.

Lessons learned

The AI made real mistakes, and the useful habit was checking results instead of trusting reports. Three examples:

  • A commit that wasn't. Claude reported the debug-mode page as committed, but a stale file sync meant the commit held only a README line. It was caught later by comparing file hashes, and since then every transfer is verified by hash before committing.
  • A cleanup that deleted everything. A script meant to remove truncated object files found no llvm-nm on its PATH and treated every object as bad. Only scratch files were lost, and it cost a 10-minute rebuild.
  • A page that only worked in one place. The demo looked right in Claude's preview, but on the engineer's own web server the debugger prompt showed in Run mode. The preview host had been adding a doctype and a [hidden] rule the page relied on; the engineer's screenshot exposed it, and the page is now a complete standalone HTML file.

Other lessons: be honest about limits (the laptop sandbox had no package manager, so tools such as dtc were built in the cloud and copied in), measure before claiming (wasm's 2x slowdown is a measured number), and keep upstream code pristine so updates stay cheap.

Try it yourself

On Ubuntu 22.04 or 24.04 (x86_64), the whole Spike pipeline is three commands, about 20 minutes of build time on 2 cores:

git clone --recurse-submodules https://github.com/premjithav/riscv-spike-web.git
cd riscv-spike-web
./scripts/setup-tools.sh --install-deps   # apt packages, RISC-V GCC, Emscripten
./scripts/build-all.sh                     # native + wasm Spike, tests, verify, demo
make serve                                 # http://localhost:8080

Run a program with the Node.js build, or debug it interactively:

node dist/node/spike.js --isa=rv64gc -m256 --dtb=dtb/rv64gc.dtb build/bench/hello.riscv
node dist/node/spike.js -d --isa=rv64gc -m256 --dtb=dtb/rv64gc.dtb build/bench/hello.riscv

In the browser demo, switch to Debug and try until pc 0 main, then reg 0 sp, r 5 and Undo last.

The setup guide, design notes and update procedure are in the repository's docs/ folder.
